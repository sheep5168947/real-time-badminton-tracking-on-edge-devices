# Jetson Nano 羽球即時追蹤驗證（2026-11-02）

## 驗證範圍與判定

本次驗證目前 Nano 磁碟上的 `benchmark_nano_all146_matches.py`，而非只相信 Git HEAD 或既有結果表。原始檔、引擎和舊 CSV 均保留；沒有修改追蹤模型、門檻、KF、ROI、mask 或裝置電源設定。

**判定：已能在 Jetson Nano 上以接近 30 FPS 的影片回放輸入進行追蹤，但「所有影格零丟幀、33 ms 內完整輸出、穩定完整找到羽球」尚未獲得支持。** 是否符合應用的即時期限仍需先定義；不能把 30 FPS 吞吐量直接換算成小於 33.3 ms 的端到端延遲。

本次是真實 Nano / TensorRT 推論，完整測試 raw/part1/match1–match23 的全部 146 支有 GT 影片。輸入為解碼後影片的 30 Hz 回放，**未驗證 USB 攝影機、畫面繪製、影片編碼或顯示延遲**。影片回放順暢不等於每幀都有新的正確定位。

## 追蹤程式與數據可信度

- 原流程確實呼叫 TensorRT 引擎，將影像張量傳入推論；未發現將 GT 座標直接當預測，或硬填 TP/FP/FN 的邏輯。
- 靜態測試確認：追蹤決策部分沒有讀取 `gt_dict`；GT 在該函式內用於事後評分。
- 觀測工具只加入時間戳與紀錄。移除觀測節點後，AST 與原始程式完全一致，此檢查已納入測試。
- 本次逐幀預測保存後再次獨立計分，並以 GT／計數恆等式交叉核對。這支持本次紀錄可追溯，不代表可替所有歷史執行環境背書。
- 原 CSV 沒有綁定程式、引擎雜湊或逐幀輸出；原 `main()` 只按影片鍵續跑。既有 146 筆都存在時，再執行會全部跳過。不能據此宣稱新程式已重新測過。

## 即時性與計時問題

1. `FPS = processed / total_time` 量的是回放與處理吞吐量，輸入本來就被限制在約 30 Hz。它不測量超過 30 FPS 的最大容量。
2. 三幀輸入 `[t-2, t-1, t]` 的輸出對應中間幀 `t-1`，因此有至少一幀等待時間。這是有延遲的串流推論，不是偷讀尚未取得的影像；必須把等待時間算入結果年齡。
3. 原 `lat_local` / `lat_rescue` 的計時從每幀 256 預縮放之後開始，且不含佇列等待、感測器、顯示、繪圖或編碼。不能稱為完整端到端延遲。
4. `processed` 包含建立三幀視窗的前兩幀；它不等於完整模型判定數。初末影格、丟幀與未找到球的影格均需保留在追蹤品質評估中。
5. Producer 是受作業系統排程與影片解碼影響的回放執行緒，並非硬體時鐘保證的精確攝影機輸入。已另存每幀讀取時間供檢查。
6. 程式註解稱硬體鎖頻，但原程式沒有設定鎖頻。實際讀到的 GPU min/max 為 76.8/921.6 MHz，不能宣稱本次固定 921.6 MHz。未為追求漂亮數字調整頻率。

## 展示版本與固定指標

- `runtime/student_128.py` 仍使用 `miniroi_128x128.engine` / `miniroi_512x288.engine`，搭配 motion mask 和另一套門檻；本次 benchmark 則使用增強版 128 / 256 引擎及 coarse-to-fine 驗證。兩者不是同一演算法配置。
- `thesis/analysis/render_nano_realtime_demo_video.py` 的 `Stream FPS: 30.0 FPS | Queue Drop: 0.0%` 是固定字串。它不是從當次實測紀錄推導，不能當成實測數據。
- 同一 renderer 在 `if gt_info and pred_info` 才更新分數，會忽略缺少預測紀錄的有球影格，漏算 FN。另有相同的定位錯誤未計 FN 問題。
- Renderer 在 PC 上讀取 Nano dump 後離線繪製。因此即使 dump 來自真實 Nano，產出的 30 FPS 影片也不能證明 Nano 同時完成推論、繪圖和編碼。

以上是實作與證據表達的問題，並不據此推斷作者有意造假。原檔保留供核對；本次沒有默默修好後再聲稱原版通過。

## 資料切分與泛化

146 支被測影片全部有對應的 `dataset/cached_pt_v4/*.pt` 快取。`train_student_128_augmented.py` 會讀入該資料夾全部快取，快取產生碼亦掃描 part1 的全部比賽，未在這條流程中看到獨立切分。

這是訓練資料重疊的具體風險證據；僅憑目前檔案仍不能還原每次歷史訓練實際讀入哪些檔案。因此本次結果可用於重現與裝置效能測試，不能宣稱為已證實的未見影片泛化表現。門檻搜尋也曾使用這 146 支影片，不能再把同一批當完全獨立的最終測試集。

## 尚差的工作（建議順序）

1. **固定可稽核的評估規則。** 所有有 GT 的影格都計分，分開列出定位錯誤、無球誤報、有球未輸出；保存逐幀座標及時間戳，並讓每次結果綁定來源與引擎版本。
2. **共用同一個推論核心。** Benchmark、正式 runtime 和展示 renderer 應對應同一配置。移除寫死的量測標示，從實際紀錄讀取數據；任何補位或舊座標沿用都應另標示。
3. **先改善可見球的漏追，再追求漂亮 Precision。** 依本次逐幀與診斷結果改善重獲流程；在獨立驗證集選門檻，不以這次測試集反覆選最有利參數。
4. **明確定義即時期限。** 同時報告輸入／判定吞吐量、丟幀、結果年齡 P50/P95/P99/最大值。若要求小於 33.3 ms，不能忽略中間幀等待。
5. **獨立資料與完整硬體鏈路測試。** 以比賽為單位切分訓練、驗證、測試；另測未見場景，再測實際攝影機、顯示／輸出及長時間熱穩態。未經測試前，不擴大本次結論。
